# 需求分析与标准格式

本技能是**背景知识**，不是可执行命令。它描述「标准需求描述格式是什么样的、如何判断一段需求属于哪种格式」，不描述「执行什么步骤」。

**适用时机（持续生效）**：用户发送**开发需求**（功能描述、实现请求、验收期望），或要求分析、评审、改写、生成需求描述时，先识别其描述方式，再按下面规则回应。

## 标准需求格式速览（共 11 种）

| # | 格式 | 中文句式骨架 |
| --- | --- | --- |
| 1 | EARS 普适 | 系统应 [行为]（无触发条件） |
| 2 | EARS 事件驱动 | **当** [触发]，系统应 [行为] |
| 3 | EARS 状态驱动 | **在** [状态] **下**，系统应 [行为] |
| 4 | EARS 可选特性 | **若/在具备** [特性] **时**，系统应 [行为] |
| 5 | EARS 非期望行为 | **若** [异常/错误]，**则**系统应 [处理] |
| 6 | EARS 复杂 | 当…且如果…，系统应… |
| 7 | 用户故事 | 作为 [角色]，我想要 [功能]，以便 [价值] |
| 8 | 用例 | 参与者 + 主流程（1→2→3）+ 备选流程（A1：…） |
| 9 | Gherkin/BDD | 给定 [前置]，当 [触发]，那么 [结果] |
| 10 | 需求模式 | 系统应 [具体技术/量化指标]（如 JWT、2 秒内、403） |
| 11 | 决策表 | 条件列（…）→ 结果列，每行一种组合 |

## 判断与回应（核心规则）

1. **识别**：对照速览表判断用户描述最接近哪种；一段话可组合多种句型（如「事件驱动 + 非期望行为」），分别指出
2. **匹配到**：先简短说明识别结果，再继续正常分析；需补全条件或行为时，用**同一句型**给一条改写示例
3. **都不匹配**（模糊、口语化、缺条件或行为）：说明不符合规范，按意图推荐格式并给出 1 条具体改写示例——状态行为→事件驱动；谁要什么/排优先级→用户故事；完整操作步骤→用例；怎么验收→Gherkin；安全/性能/合规→需求模式；多条件组合→决策表
4. **生成要求**：句子必须**可验证**——有明确的触发/状态/条件和可观察的行为或量化指标；避免「别太卡」「好用」这类无法验收的表述
