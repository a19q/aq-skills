# GitLab PR（MR）创建

用 `glab` CLI（已完成登录认证）完成建分支、提交、推送、创建 Issue/MR、补设 assignee/里程碑/审批规则的全流程。

四种场景：①特性 `feat/`、②修复 `fix/`、③大杂烩 `misc/`（draft）、④开发阶段大分支 `release/`（draft）。触发条件、调用示例与步骤差异见 [references/workflows.md](references/workflows.md)。

四种场景都必须同时创建 Issue 和 PR/MR：**Issue 标题与 PR 标题逐字符一致、Issue body 为空**。

## 场景⓪

**用户只输入 `/pr-creation`、本次调用没有指定要提交的改动 → 一律场景⓪**，只输出四种场景示例，不执行任何动作。

对话里有什么（需求号、base 分支、里程碑、历史话题、甚至已存在的 diff）都不改变判定：这些都不是「本次要提交的改动」。只有本次调用明确说了要提交什么（如「把这次改动提个 PR」「修复登录超时并提 PR」），才走对应正式场景。拿不准时走场景⓪。

## 执行顺序（强制闸门）

1. **环境探测**：跑 [references/glab-api.md](references/glab-api.md) 的「环境探测」。`glab` 未登录或不可用时停止，告知用户先 `glab auth login`
2. **安全扫描**：见下方「安全闸门」；命中即终止
3. **远端预检**：跑 [references/glab-api.md](references/glab-api.md) 的「远端预检」。当前分支就是 base 分支、远端已有同名分支、该分支已有打开的 MR——任一命中即**停止并汇报，等用户指示**；不改分支、不推送、不建 MR，也不「顺手复用」已有 MR
4. **命名自检**：按 [references/naming.md](references/naming.md) 的 9 项逐条对照，任一不通过即停止
5. **输出任务清单表格**：未输出表格和自检结论，不得建分支、不得调用任何 GitLab API
6. **执行**：建分支 → 提交 → 推送 → 建 Issue → 建 MR → 补设，命令见 [references/glab-api.md](references/glab-api.md)

## 需求号识别（整个对话范围）

需求号**不要求用户在任务指令里特意指出**，必须主动从**整段对话**中识别，命中就直接填进任务清单表格——**不要先反问「有没有需求号」**；未命中则填「无」。

- **来源**：当前与历史消息、粘贴的需求描述、引用的 Issue/MR 链接或标题、PMX 编号、`需求号`/`需求编号`/`REQ` 等标注
- **格式**：`#<数字>`、`需求号[:：]?\s*<数字>`、`PMX[:：#\s]?\d+`、需求链接末段数字等
- **命中唯一需求号**：分支名、PR/Issue 标题、body 的 `PMX:#<编号>` 与 `PMX LINK` 编号**都必须**使用它，不再问用户
- **命中多个不同需求号**：无法确定用哪个，**立即停止**，列出候选项请用户指定
- **整段对话都没有**：不加，分支无数字段，标题直接以首字母开头

不要输出「分支名没有需求号，是否要加上？」这类询问；表格里出现 `#<数字>` 即是告知。

## 任务清单表格（执行前强制输出）

- 须含「需求号」行（命中填 `#<数字>`，未命中填「无」）与「label」行（未指定填「待用户确认」）
- 命中需求号时，分支名须含该数字段、PR 名称与 Issue 名称须以 `#<数字> ` 开头，三者数字一致
- 表格中的 PR 名称与 Issue 名称必须逐字符一致
- 名称字段（分支名、PR 名称、Issue 名称）用户可指定但**不豁免命名约束**：不通过则**立即停止**，说明原因，等用户给出合规名称或授权改写
- 里程碑、base 分支等非名称字段按用户指定
- 表格后附一行命名自检结论（格式见 [references/naming.md](references/naming.md)）

字段与各场景示例见 [references/workflows.md](references/workflows.md)。

## PR body

**只有一种格式，严格遵守**：逐行照抄 [references/body-template.md](references/body-template.md)，五行固定顺序、不得增删小节，不写二级小节、不用列表罗列要点。

## 参数默认值

用户本次说明的值优先，未说明时用下表默认；用户说明的名称仍须通过命名约束。

| 项目      | 默认                                                                                                    |
| --------- | ------------------------------------------------------------------------------------------------------- |
| 需求号    | 主动从整段对话识别；命中则分支名、PR/Issue 标题、`PMX:#` 都必须使用；命中多个则停止确认；完全没有才不加 |
| base 分支 | 先探测仓库默认分支，探测不到用 `main`                                                                   |
| 分支名称  | 按改动内容命名 `<场景前缀>/<kebab-case-描述>`（有需求号则前置 `<需求号>-`），全名 ≤25 字符              |
| 里程碑    | 取项目**最新的激活里程碑**；取不到则留空并告知用户。用户指定了但不存在则**创建它**                      |
| assignee  | 当前 glab 登录用户（本人）                                                                              |
| 审批人数  | `1`                                                                                                     |
| label     | **不自动设置**；Issue 与 MR 建好后提醒用户是否需要绑定，用户给出标签名再用 API 补设                     |

## 安全闸门（命中即终止）

提交前检查暂存/改动内容，出现以下字段且**有值**即终止并警告，**阻止提交**：`cscKeyPassword`、`token`（作为敏感凭证字段时）、其他明显的密码/密钥/私钥字段。

```bash
git diff --cached -G'(cscKeyPassword|token)' --name-only
```

即使确认是测试/占位值或误报，也要先向用户指出并取得确认后再继续。

## 执行约定

- 多行参数（body 等）一律走临时文件（`--body-file` / `-F`），不塞进命令行；临时文件默认放 `~/Downloads`（Windows：`%USERPROFILE%\Downloads`）
- 每条外部动作（push、建 Issue、建 MR、改审批规则、绑定 label）执行前给用户一句简短说明
- 收尾必须**提醒 label**：问用户是否需要绑定，给出标签名才补设
- 完成后汇报：分支名、Issue 号/链接、MR 号/链接、base 分支、里程碑、draft 状态、label，并附任务清单表格
