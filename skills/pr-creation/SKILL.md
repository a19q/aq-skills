# GitLab PR（MR）创建

用 `glab` CLI（已完成登录认证）完成建分支、提交、推送、创建 Issue/MR、补设 assignee/里程碑/审批规则的全流程。

## 场景

四种场景，各自的前缀、draft、触发条件、调用示例与步骤差异见 [references/workflows.md](references/workflows.md)：

| 场景             | 前缀       | draft | 适用                           |
| ---------------- | ---------- | ----- | ------------------------------ |
| ① 特性           | `feat/`    | 否    | 一次独立功能                   |
| ② 修复           | `fix/`     | 否    | 一次缺陷修复                   |
| ③ 大杂烩         | `misc/`    | 是    | 多主题混杂、不好归类的一批改动 |
| ④ 开发阶段大分支 | `release/` | 是    | 一个开发阶段的集成分支         |

四种场景都必须同时创建 Issue 和 PR/MR，**Issue 标题与 PR 标题逐字符一致、Issue body 为空**；PR body 用中文且含 `Close #<ISSUE_ID>`。

无参数调用：整段对话都未提供任何任务信息（无改动说明、无分支名、无需求号、无场景指示、无 base 分支、无里程碑）时，不执行任何动作，只输出四种场景示例并提示用户选择场景或补充描述。需求号本身不算独立任务信息；只要对话中还有其他任一项信息，就按对应正式场景处理。

## 需求号识别（整个对话范围，强制使用）

需求号**不要求用户在任务指令里特意指出**，Agent 必须主动从**整段对话**中识别，而不是只看当前这一句。用户未指明时默认静默识别，命中就直接填进任务清单表格并显式列出——**不要先反问「有没有需求号」**，表格是用户的第一道确认点；未命中则表格填「无」。

- **识别来源**：用户当前与历史消息、粘贴的需求/任务描述、引用的 Issue/MR 链接或标题、PMX 编号、`需求号`/`需求编号`/`REQ` 等标注。
- **识别格式**：`#<数字>`、`需求号[:：]?\s*<数字>`、`PMX[:：#\s]?\d+`、需求链接末段数字等。
- **命中唯一需求号**：分支名与 PR/Issue 标题**都必须**使用该需求号，不必再让用户确认、也不必再问一次。这是强制项，不是可选项。
  - 分支名：`<场景前缀>/<需求号>-<kebab-case>`（需求号作为第一个 kebab 段）
  - PR/Issue 标题：`#<需求号> <首字母大写的标题>`（如 `#8964 Add image marker`）
  - body：`PMX:#<需求号>` 与 `PMX LINK` 的编号都用它（格式见 [references/body-template.md](references/body-template.md)）
- **命中多个不同需求号**：无法确定用哪个，**立即停止**，列出候选项请用户指定后再继续。
- **整段对话都没有需求号**：不加，分支无数字段，标题直接以首字母开头。

> **反模式**：不要输出「分支名没有需求号，是否要加上？」这类询问。既然已在整段对话中找到需求号，就直接用；表格里出现 `#<数字>` 即是告知。

## 任务清单表格（执行前强制输出）

在执行 `git checkout -b` / `git switch -c` 等建分支动作，或任何 `glab api` 调用前，**必须先向用户输出任务清单表格**。表格字段与各场景填写示例见 [references/workflows.md](references/workflows.md)「生成的任务清单表格」。

- 表格须包含「需求号」行，命中时填 `#<数字>`，未命中填「无」
- 命中需求号时，表格里的分支名必须含该数字段、PR 名称与 Issue 名称必须以 `#<数字> ` 开头；三者数字一致，不得只在其中一处出现
- 表格中的 PR 名称与 Issue 名称必须逐字符一致
- 名称字段（分支名、PR 名称、Issue 名称）用户可指定但**不豁免命名约束**：通过则采用；不通过则**立即停止，不建分支、不调用 API**，说明不合规原因，等待用户给出合规名称或授权改写
- 里程碑、base 分支等非名称字段按用户指定
- 输出表格的**同时**要按「命名约束」表逐条自检，并在表格后附一行自检结论；不跑任何校验脚本
- 未输出表格、未附自检结论，不得建分支、不得调用任何 GitLab API

## 命名约束（强制，违反即停止）

规则优先级最高，任何来源（用户描述、Git 历史、模板、对话历史）产生的名称都要逐条对照校验，任一不通过即停止，不进入下一动作。

| #   | 校验项            | 判定方法                                                                                                                                                                                                         |
| --- | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 分支格式          | 前缀只能是 `feat/` `fix/` `misc/` `release/` 四种之一，其他前缀（`hotfix/`、`chore/`、`docs/` 等）一律不合规；无前缀时补场景默认前缀。全名只用小写字母、数字、`-`、`/`，`/` 只出现一次                           |
| 2   | kebab 段          | 去掉前缀与首段需求号后，至少 2 个单词，且至少一个单词含字母（排除 `misc/20260907`、`release/1-2` 这类纯数字）                                                                                                    |
| 3   | 长度              | 全名（含前缀与需求号），超长先缩写/精简单词                                                                                                                                                                      |
| 4   | 禁止日期/版本式名 | `misc/20260907`、`misc/2026-0907`、`release/1.2.0`、`release/1-2` 一律不合规。用户给定这类名称时可建议改为语义化 kebab（如 `release/phase-one-release`），但未经确认不得建分支、不得调用 API；用户坚持则停止执行 |
| 5   | 标题大小写        | 去掉 `#<需求号> ` 前缀后首个字母大写、其余字母全小写；`#` 与数字之间、数字与正文之间各一个空格；除需求号 `#` 外不得出现其他特殊字符                                                                              |
| 6   | 逐词对齐          | 分支去掉前缀、剔除首段需求号后的 kebab 拆词，与标题去掉 `#<需求号> ` 后的单词**逐一对应、数量一致**                                                                                                              |
| 7   | 需求号三处一致    | 对话命中的需求号 = 分支首段数字 = 标题 `#<数字>`，三者完全相同；对话有需求号而分支或标题缺该数字段即失败                                                                                                         |
| 8   | Issue = PR        | Issue 标题与 PR 标题逐字符完全一致（含 `#`、空格、大小写），禁止单方面改写；PR 标题变更时同步变更                                                                                                                |
| 9   | 表格与执行一致    | 最终建分支/建 Issue/建 MR 用的名称，与已输出的任务清单表格逐字符相同；中途改名必须重出表格                                                                                                                       |

用户明确给出名称或标题时**不豁免**以上规则；违反则立即停止，不建分支、不调用 API、不擅自改写，说明违反项后等待指令。

**数字段歧义**（分支首段是纯数字时）：`0907 Fix` 与 `#8964 Image marker` 去掉 `#` 后形态相同，字面上无法区分「数字属正文」和「需求号漏写 `#`」。按需求号识别规则处理：

- 整段对话无需求号 → 数字属正文，分支与标题都不带 `#`（`misc/0907-fix` + `0907 Fix`），合法
- 整段对话有需求号 → 该数字必须是那个需求号，标题必须写成 `#<数字>`；分支首段数字与需求号不一致即停止
- 无法判断 → 停止并请用户确认，不得自行猜一个

自检结论随任务清单表格一起输出，用一行说明各项是否通过：

```text
命名自检：①分支格式 ✓ ②kebab 段 ✓ ③长度 ✓ ④无日期版本 ✓ ⑤大小写 ✓ ⑥逐词对齐 ✓ ⑦需求号三处一致 ✓ ⑧Issue=PR ✓ ⑨表格一致 ✓
```

## PR body 要求

- 用**简体中文**，只描述相对最终代码的功能，忽略开发过程、废弃方案、中间演变、重构改名等
- 整体概括性强，默认不超过 100 字（按用户要求可调）
- 必须包含 `Close #<ISSUE_ID>` 以关闭配套 Issue
- 命中需求号时，`PMX:#<编号>` 的编号取该需求号
- 格式参考 [references/body-template.md](references/body-template.md)

## 参数规则（用户说法优先）

一切以用户本次说明的值为准，未说明时用下表默认；用户说明的名称仍须通过命名约束。

| 项目                | 用户说明时                                  | 未说明时的默认                                                                                                           |
| ------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 需求号 `#数字` 前缀 | 按用户给的数字，格式为 `#<数字>` + 一个空格 | **主动从整段对话识别，不反问用户**；命中则分支名与 PR/Issue 标题都必须使用；命中多个不同需求号则停止确认；完全没有才不加 |
| base 分支           | 按用户指定（如 `main`）                     | 先探测仓库默认分支，探测不到用 `main`                                                                                    |
| 分支名称            | 按用户指定（无前缀时补场景默认前缀）        | 按改动内容命名：`<场景前缀>/<kebab-case-描述>`（有需求号则前置 `<需求号>-`），全名 ≤25 字符                              |
| 里程碑 milestone    | 按用户指定；指定了但不存在则**创建它**      | 取项目**最新的激活里程碑**；取不到则留空并告知用户                                                                       |
| body 字数           | 按用户说明                                  | 中文**不超过 100 字**                                                                                                    |
| assignee            | 按用户指定用户名                            | 取当前 glab 登录用户（本人）                                                                                             |
| 审批人数            | 按用户指定                                  | `1`                                                                                                                      |

## 安全闸门（最高优先级，命中即终止）

提交前检查本次暂存/改动内容，若出现以下安全字段且**有值**，立即终止并警告，**阻止代码提交**：`cscKeyPassword`、`token`（作为敏感凭证字段时）、其他明显的密码/密钥/私钥字段。

```bash
# 命中即停，不执行 commit/push/MR
git diff --cached -G'(cscKeyPassword|token)' --name-only
```

即使确认是测试/占位值或字段名误报，也要先向用户指出并取得确认后再继续。

## 执行约定

- 多行参数（body 等）一律走临时文件（`--body-file` / `-F`），不要在命令行里塞多行字符串
- 临时文件用户未指定位置时，默认放系统下载文件夹 `~/Downloads`（Windows：`%USERPROFILE%\Downloads`），用完可保留或清理
- 每条外部动作（push、建 Issue、建 MR、改审批规则）执行前给用户一句简短说明
- 完成后汇报：分支名、Issue 号/链接、MR 号/链接、base 分支、里程碑、draft 状态，并附上任务清单表格

## 环境与命令

完整命令清单（环境探测、建分支推送、提交、查里程碑/用户、建 Issue/MR、补设 assignee/里程碑/审批、设 draft）见 [references/glab-api.md](references/glab-api.md)。该文件只放 `git` 与 `glab` 命令，命名校验不在此处，见本文「命名约束」小节。

先探测：

```bash
git remote -v
which glab
glab auth status   # 应显示 Logged in to <HOST> as <USERNAME>
```

`glab` 未登录或不可用时停止，并告知用户先 `glab auth login`。
