# 场景工作流与调用示例

四种正式场景：①特性 `feat/`、②修复 `fix/`、③大杂烩 `misc/`、④开发阶段大分支 `release/`；另有 ⓪ 无参数调用（仅展示示例，不执行）。

所有正式场景执行前，必须完成 [naming.md](naming.md) 的命名约束自检与任务清单表格输出，然后再建分支或调用 GitLab API。命名校验不跑脚本，而是在输出任务清单表格时按 [naming.md](naming.md) 的 9 项逐条对照，并附一行自检结论。本文件给出各场景的完整调用示例与步骤差异。

---

## 场景⓪：无参数调用（仅 `/pr-creation`）

### 触发条件

**用户只输入 `/pr-creation`、本次调用没有指定要提交的改动 → 场景⓪。**

对话里有什么（需求号、base 分支、里程碑、历史话题、已存在的 diff）都不改变判定：这些都不是「本次要提交的改动」。

只有本次调用明确说了要提交什么（如「把这次改动提个 PR」「修复登录超时并提 PR」），才走对应正式场景。拿不准时走场景⓪。

> 场景①~④的示例表格中「需求号」一列填「无」，是为了给未命中需求号的情形留出对照。**对话中已出现需求号时，一律按场景①「带需求号的完整示例」处理，分支名与 PR/Issue 标题都必须带上**。

### 行为

**不执行任何动作**：不探测环境、不建分支、不提交、不推送、不调用任何 GitLab API、不创建 Issue/MR。只在对话中依次输出下方场景①~④的**完整示例**（含用户说法与任务清单表格），末尾附固定提示。

### 末尾固定提示

```text
以上为四种场景的标准示例。
请选择场景①/②/③/④，或直接描述本次改动（改动内容、base 分支、需求号、里程碑等），我再生成任务清单表格并开始执行。
```

## 场景①：特性分支 PR

### 触发条件

用户说「提交代码并创建 PR」「提交更改并创建 MR」「新增功能提 PR」「新建分支提 PR」等。

基准场景，其余场景只列差异。

| 项目     | 值                                    |
| -------- | ------------------------------------- |
| 分支前缀 | `feat/`                               |
| 分支命名 | `feat/<kebab-case>`，无前缀补 `feat/` |
| 提交     | 提交本次更改，信息简单即可            |
| draft    | 否                                    |
| 适用     | 一次独立功能                          |

### 完整调用示例

用户说法：`把这次改动提个 PR`

**生成的任务清单表格：**

| 项目        | 值                      |
| ----------- | ----------------------- |
| 场景        | ① 特性分支 PR           |
| 需求号      | 无                      |
| 分支名称    | `feat/add-image-marker` |
| 分支前缀    | `feat`                  |
| PR 名称     | `Add image marker`      |
| Issue 名称  | `Add image marker`      |
| base 分支   | `main`                  |
| 里程碑      | `1.2.0`                 |
| assignee    | 当前登录用户            |
| 审批人数    | `1`                     |
| draft       | 否                      |
| label       | 待用户确认              |
| Close issue | `#1024`                 |

**命名推导**：分支 `feat/add-image-marker`（21 字符）→ 忽略前缀 `add-image-marker` → 标题 `Add image marker`，逐词对齐，Issue 标题完全一致。

### 带需求号的完整示例（对话中已有需求号时）

用户说法：`把这次改动提个 PR，需求号是 #8964`——**更常见的情形是用户不主动提**，例如用户只贴了一段需求描述并附上 Issue 链接 `https://gitlab.example.com/team/project/-/issues/8964`。两种情形下 Agent 都必须自行识别出 `#8964`，**不要反问用户「要不要加需求号」**。

**生成的任务清单表格：**

| 项目        | 值                           |
| ----------- | ---------------------------- |
| 场景        | ① 特性分支 PR                |
| 需求号      | `#8964`                      |
| 分支名称    | `feat/8964-add-image-marker` |
| 分支前缀    | `feat`                       |
| PR 名称     | `#8964 Add image marker`     |
| Issue 名称  | `#8964 Add image marker`     |
| base 分支   | `main`                       |
| 里程碑      | `1.2.0`                      |
| assignee    | 当前登录用户                 |
| 审批人数    | `1`                          |
| draft       | 否                           |
| label       | 待用户确认                   |
| Close issue | `#1024`                      |

**命名推导**：需求号 `#8964` → 分支 `feat/8964-add-image-marker`（28 字符）**超出 25 字符上限**，须先精简 kebab 描述：`feat/8964-image-marker`（22 字符）→ 忽略前缀、剔除首段需求号 `8964` → 标题 `#8964 Image marker`，逐词对齐，Issue 标题完全一致。body 的 `PMX:#8964` 用同一个编号。

**反模式**：命中需求号却生成 `feat/add-image-marker` + `Add image marker`（三处都没带需求号），或只在标题带、分支不带。这是需求号漏用，属执行错误。

### 步骤

1. **环境探测** → 确认 `glab` 可用、已登录
2. **安全扫描** → 检查暂存区敏感字段，命中即终止
3. **确认参数** → 需求号（**从整段对话自行识别，不反问用户**；命中即强制用于分支与标题）、base 分支、里程碑、body 字数
4. **远端预检** → 查当前分支、远端同名分支、该分支已有 MR（[glab-api.md](glab-api.md)「远端预检」）；命中任一项即停止汇报，等用户指示
5. **命名三步** → 分支 `feat/<kebab-case>`（无前缀补 `feat/`）→ PR 标题逐词对齐 → Issue 标题同 PR（有需求号则分支前置 `<需求号>-`、标题以 `#<需求号> ` 开头）
6. **输出任务清单表格** → 硬性闸门；同时按 [naming.md](naming.md) 的 9 项逐条自检，并附一行自检结论（不跑脚本）
7. **创建分支** → `git checkout -b <BRANCH>`
8. **提交代码** → `git add . && git commit -m "简短提交信息"`
9. **推送** → `git push -u origin <BRANCH>`
10. **创建 Issue** → 标题与 PR 逐字符一致，body 为空
11. **创建 MR（PR）** → 标题同 PR，body 走临时文件并含 `Close #<ISSUE_ID>`
12. **补设** → assignee（本人）、里程碑（按规则取或创建）、审批人数（默认 1）
13. **提醒 label** → 询问用户是否需要绑定 label；用户给出标签名才用 API 补设，不确认不设
14. **汇报** → 分支名、Issue 链接、MR 链接、base 分支、里程碑，并附任务清单表格

## 场景④：开发阶段大分支 PR

### 触发条件

用户说「大分支」「开发阶段大分支」「集成阶段分支」「release 分支」等。

除下表差异外，其余同场景①。

| 项目     | 值                                               |
| -------- | ------------------------------------------------ |
| 分支前缀 | `release/`                                       |
| 分支命名 | `release/<语义化 kebab>`；**禁止纯版本号分支名** |
| 提交     | 随当前状态（沿用，不强制提交）                   |
| draft    | 是，创建后调用 API 设为 WIP/Draft                |
| 里程碑   | 版本号可与需求版本对应（如 `1.2.0`）             |
| 适用     | 一个开发阶段的集成分支                           |

### 完整调用示例

用户说法：`创建开发阶段大分支提 PR`

**生成的任务清单表格：**

| 项目        | 值                          |
| ----------- | --------------------------- |
| 场景        | ④ 开发阶段大分支 PR         |
| 需求号      | 无                          |
| 分支名称    | `release/phase-one-release` |
| 分支前缀    | `release`                   |
| PR 名称     | `Phase one release`         |
| Issue 名称  | `Phase one release`         |
| base 分支   | `main`                      |
| 里程碑      | `1.2.0`                     |
| assignee    | 当前登录用户                |
| 审批人数    | `1`                         |
| draft       | 是                          |
| label       | 待用户确认                  |
| Close issue | `#1027`                     |

**命名推导**：分支 `release/phase-one-release`（25 字符，上限内）→ 忽略前缀 `phase-one-release` → 标题 `Phase one release`，逐词对齐。

**带需求号变体**：对话中命中 `#8967` → `release/8967-phase-one-release`（30 字符）超长，先精简为 `release/8967-phase-one`（22 字符）→ 标题 `#8967 Phase one`。

**反例**：`release/1.2.0` 为纯版本号分支，不合规，须改为语义化 kebab（如 `release/phase-one-release`），版本号只放里程碑字段。
