# 前端开发通用规则

> 适用范围：所有前端项目，与技术栈无关。框架专项规则见同目录 `react.md` / `vue.md` / `electron.md`，语言层规则见 `ts.md`。

## 一、协作与开发流程

### 核心原则

- **确认优先**：任何不确定的技术细节，先向用户提问确认再编码。处理过程中遇到问题（设计缺失字段、逻辑不通顺等）要及时确认，不要自行猜测补齐。
- **任务拆分**：尽可能把任务拆成多个小任务，依次完成并逐个检查。
- **仔细严谨**：仔细排查问题，不要马虎。不要凭空生成 API，也不要凭空修改或生成 `d.ts` 类型声明；遇到缺失应询问。
- **方案建议**：路线不清晰时可给出多个方案；给出多个方案时，必须同时给出推荐方案及理由。

### 何时先出设计方案

- **需求已足够清晰、改动范围明确、风险可控**时：做简短确认后可直接开始修改，**不需要**先单独输出设计文档。
- **需求不清晰、存在多个方案分叉、影响面较大或风险较高**时：先输出设计方案，与用户确认后再实施。

### 工程约定

- 包管理器统一使用 `yarn`，不使用 `npm`。
- **可读性与可维护性**：清晰的命名、简洁的逻辑、必要时用 JSDoc 注释。
- **错误处理**：实现健壮的错误处理，返回具有实际意义的错误信息。
- **SOLID**：遵循单一职责、开闭原则等。
- **DRY**：避免代码冗余，不要重复自己。

## 二、命名规范

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 文件目录 | kebab-case | `react-button` |
| 组件文件 | PascalCase | `MyComponent.tsx` |
| 函数 | camelCase（API 函数例外，用 PascalCase） | `getUserList` / `GetUserList` |
| 变量 | camelCase | `userName` |
| 常量 | UPPER_CASE | `MAX_COUNT` |
| 类型 | PascalCase | `UserInfo` |
| 接口 | `I` + PascalCase | `IUser` |
| 组件 Props 接口 | 必须以 `Props` 结尾 | `IButtonProps`、`IModalProps` |

- **API 函数用 PascalCase** 是本项目的特殊约定，用于在调用处一眼区分「网络请求」与「本地函数」，如 `GetUserList()`。其余普通函数一律 camelCase。
- **组件 Props 接口**必须同时满足 `I` 前缀 + `Props` 后缀，如 `IUserPanelProps`。

## 三、组件与文件结构

### 组织方式

- **优先复用**：优先使用框架自带或项目 `components` 目录下已有的组件，不要重复实现。
- **组件封装**：重复出现的代码应尽可能封装成通用组件或 hook。
- **组件化抽象**：可组件化或抽象化的地方，主动进行优化与封装。
- **文件结构**：新增组件使用「文件夹 + `index`」形式，如 `react-button/index.tsx`。

### 导出与导入

- **具名导出**：不要 `function` 声明 + `export default`，统一使用 `export const` 具名导出。
- **禁止桶导出**：不要使用 Barrel exports（`index.ts` 里 `export * from ...` 聚合再导出）。
- **保持引用路径一致**：同一模块在各处的引用路径写法统一（相对路径 + 后缀写法一致），避免被模块缓存当成两个模块——Electron 主进程场景尤其关键，见 `electron.md`。

### 文件与工具

- **文件拆分**：单文件超过 500 行就要考虑拆分优化；确认可拆分后，需询问用户同意再执行。
- **工具函数**：需要工具函数时，先在 `lib` 或 `utils` 目录查找，找不到再自己实现。
- **深拷贝**：后续操作存在影响原对象风险时，优先使用 `structuredClone`；禁止使用 `JSON.parse(JSON.stringify(...))` 这类有信息丢失风险的方案。

### 职责划分

- **父子组件职责**：当某段逻辑仅在子组件内即可完成时，不要新增 `props` 让子组件通知父组件来完成。
- **副作用模块边界**：抽取逻辑时，如果功能模块是独立的、且存在多个观察者，应让它作为**副作用模块**在被导入的文件中自行生效，而不是导出 `init()` 之类的方法再由导入方手动触发——手动触发更容易被重复调用。Electron 主进程的模块缓存细节见 `electron.md`。

## 四、测试规范

- **先确认再写测试**：需要新增测试、补充测试文件或扩大测试范围时，必须先询问用户是否允许编写测试。
- **优先函数逻辑测试**：测试优先聚焦纯函数、工具函数、复杂业务函数等可稳定验证的逻辑。
- **简单函数可减免**：逻辑非常直接、收益较低的简单函数不强制补测试。
- **避免不必要的重测试**：非必要不主动编写 UI 测试、E2E 测试或大规模集成测试。

## 五、样式与 UI 还原

- **原子样式优先**：项目若配置了原子样式（Tailwind、NativeWind），优先使用原子样式实现。
- **类名拼接**：采用原子样式时，需按逻辑动态拼接类名的场景尽量避免模板字符串，统一使用 `cn` 工具函数处理，确保样式合并可预测、避免冲突。

  ```tsx
  // 推荐：条件合并交给 cn
  <button className={cn('px-4 py-2', active && 'bg-primary text-white')} />

  // 不推荐：模板字符串手写拼接
  <button className={`px-4 py-2 ${active ? 'bg-primary text-white' : ''}`} />
  ```

- **弹窗高度**：页面弹窗组件高度不要溢出，避免导致遮罩层出现滚动条。
